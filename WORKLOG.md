# WORKLOG — EduHub (ВКР, текущий этап)

> **Handoff:** после правок на этом ПК — `git add`, `git commit`, `git push`, на другом ПК — `git pull`. История чата Cursor не переносится; ориентир — этот файл + `reports/vkr/`.

## 0) Быстрый старт с любого ПК (после `git pull`)

1. Ветка: **`prediploma-journal`** (проверить: `git branch`)
2. `.venv` → `pip install -r requirements.txt` (если нужно)
3. `python manage.py migrate`
4. `python manage.py runserver`

## 1) Решения руководителя и сроки

- **Главный приоритет:** довести **формальный текст ВКР** к сдаче (сейчас — рыба + куски из практик).
- **Фичи в коде:** минимум, по возможности; в тексте можно описывать направления развития, если в приложении ещё не всё реализовано — **честно разделять** «реализовано» / «частично» / «перспектива».
- **Деплой:** руководитель не настаивает — **отдельную главу не делать**; при необходимости одна фраза в **3.7** или заключении.
- **Тестирование:** не отдельная большая глава — раздел **3.6** (ручные сценарии + при времени 1–2 автотеста).
- **Срок:** ориентир **~2 недели** (текст + точечный код), с учётом основной работы.

## 2) Подход к работе (порядок)

1. **Структура ВКР** — утверждена (см. §3).
2. **Текст по блокам** — не весь документ сразу: введение → глава 1 → … → глава 3; стиль — прикладная ВКР, без «идеального» ИИ-канцелярита, привязка к проекту EduHub.
3. **Разработка** — когда дойдём до главы 3; с **самой простой** фичи из списка (см. §5).
4. Перед защитой: сверка утверждений текста с фактическим кодом и скриншотами.

### Правила редактуры текста (для чата / самопроверки)

- Академический, но **естественный инженерный** тон; без частых «таким образом», «следует отметить».
- Не менять смысл, не выдумывать факты.
- Избегать: «готовое к внедрению», «полный цикл», «прямая угроза 152‑ФЗ» — мягче и точнее по факту прототипа.

ВВЕДЕНИЕ

1 АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И СУЩЕСТВУЮЩИХ РЕШЕНИЙ
   1.1 Описание предметной области
   1.2 Административные процессы и роли пользователей
   1.3 Анализ существующих решений
   1.4 Формирование требований к системе

2 ПРОЕКТИРОВАНИЕ ИНФОРМАЦИОННОЙ СИСТЕМЫ
   2.1 Обоснование выбора технологического стека
   2.2 Функциональная декомпозиция и UML-диаграммы
   2.3 Архитектура системы
   2.4 Проектирование базы данных
   2.5 Ролевая модель и безопасность
   2.6 Проектирование пользовательских интерфейсов

3 РЕАЛИЗАЦИЯ И АПРОБАЦИЯ ИНФОРМАЦИОННОЙ СИСТЕМЫ
   3.1 Организация процесса разработки

Глава 1–2: в основном из **преддипломной**, переписать под ВКР. Глава 3: расширить под код; **4–5 отдельных глав нет**.

## 5) Следующий шаг (продолжить с другого ПК)

1. **Текст:** блок **1.1** (или весь §1 по подпунктам) — вычитка по правилам §2; сверка с `reports/prediploma/` и черновиком `reports/vkr/`.
2. **Не начинать код**, пока не пройден хотя бы каркас главы 1 или согласованный объём текста с руководителем.
3. Когда дойдём до кода — очередность фич (MVP, от простого):
   - генерация **КТП** (даты по дням недели, без выходных/праздников → docx);
   - **полугодовые отчёты** менеджера (сводка + экспорт);
   - **МЗ** (один упрощённый шаблон, педагог);
   - по остатку времени: уведомления педагог→родитель, правка данных ребёнка, аудит.
